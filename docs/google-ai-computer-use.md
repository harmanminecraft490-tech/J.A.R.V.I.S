# Google AI + Computer Use

## Product flow

On first application launch:

1. Show a setup screen requesting the user's Google AI API key.
2. Validate the key with a minimal provider health request.
3. Store the credential locally using Windows Credential Manager (with an encrypted local fallback only when required).
4. Never place the key in source code, `.env` files generated by the app, logs, screenshots, telemetry, or Git.
5. Start the JARVIS session after successful validation.

## Runtime architecture

```text
Microphone / text
       |
       v
Google AI Provider <---- conversation/task state
       |
       | structured computer-use decision
       v
Computer Use Controller
       |
       +--> observe screenshot/window state
       +--> mouse / keyboard / window actions
       +--> filesystem / terminal tools
       |
       v
Verification
       |
       +--> success -> continue/complete
       +--> mismatch -> recover/replan
```

The model is never given unrestricted OS primitives. It receives a typed tool catalog and produces validated action requests. The local executor enforces safety, focus checks, cancellation, timeouts, and high-risk confirmation.

## Computer-use action contract

Every model action must contain:

- action name
- target/context
- typed parameters
- expected result
- verification strategy

The executor validates the action before execution and records a redacted audit event.

## Voice

Voice is an adapter rather than a hard-coded subsystem. The initial provider integrates Google AI voice capabilities where supported. `VoiceProvider` exposes `input`, `speak`, `interrupt`, and `stop`, allowing another voice transport to be substituted later.

## Google AI Hub / endpoint configuration

The initial setup accepts a Google AI API key. Provider endpoint/model identifiers are configuration values, not hard-coded secrets. If the user's account exposes a specific Google AI Hub endpoint or model identifier, it can be configured without changing the computer-use engine.
